# GitHub setup, step by step

Everything in this document is done by you. Nothing here needs me, and nothing
here touches the code — the repository is empty, the project is ready, and these
are the steps that connect the two.

Total time: about fifteen minutes, most of it waiting for a 14 MB push and a
two-minute build.

At the end you will have a URL like `https://yourname.github.io/turtle/` that
students open, that updates when you push, and that refuses to update if the
security tests fail.

---

## Before you start: two things to know

**1. The repository has to be public.**

GitHub Pages on the free plan only publishes from public repositories. Private
repositories need GitHub Pro or an organisation plan.

Public means the source is readable by anyone. For this project that is fine,
and worth checking rather than assuming:

- There are no passwords, keys, or tokens anywhere in the project — there is no
  server to hold credentials for.
- There is no student data, because the application never receives any.
- `.gitignore` keeps `node_modules/`, `dist/`, and the `Claude outputs/`
  screenshot folder out of the repository entirely.

Step 3 below has you look at the file list before the first commit, so this is
something you confirm with your own eyes rather than take from me.

**2. The 14 MB `vendor/` folder gets committed, on purpose.**

`vendor/` holds Pyodide (Python compiled to WebAssembly, 13 MB) and the
CodeMirror bundle (900 KB). Both are pinned, vendored copies. There is no build
step that fetches them, which is the whole point — the site cannot break because
someone else's CDN changed or went away, and it cannot quietly start loading a
different version of Python than the one you tested.

The practical consequences: the first push uploads 14 MB and takes a minute or
two, and the repository will show as ~14 MB. GitHub's limits are 100 MB per file
(largest here is 9.6 MB) and 1 GB per repository. There is plenty of room.

## Step 1 — Tell git who you are

Git on this machine has no name or email configured yet, and it refuses to
commit without them. Once, in PowerShell or Git Bash:

```
git config --global user.name "Mark Betnel"
git config --global user.email "mbetnel@seattleacademy.org"
```

Use the same email you sign in to GitHub with, so commits are attributed to your
account. If you would rather not have your school address in a public commit
log, GitHub can give you a `@users.noreply.github.com` address —
**Settings → Emails → Keep my email addresses private** — and you use that here
instead.

## Step 2 — Make the project a git repository

```
cd C:\Users\SAAS_User\Documents\Projects\online-python
git init -b main
```

`-b main` matters. Git 2.34 still defaults the first branch to `master`, and the
deploy workflow triggers on pushes to `main`. If you have already run a bare
`git init`, `git branch -M main` renames it.

---

## Step 3 — Look at what git is about to take

This is the step worth not skipping.

```
git add .
git status --short
```

You should see about **70 files**. Read the list. What should be there:

- `index.html`, `styles.css`, `sw.js`, `favicon.svg`, `_headers`
- `src/` — the application
- `vendor/` — 6 files, the Pyodide and CodeMirror copies
- `test/` — the suites and their reference screenshots
- `.github/workflows/deploy.yml`
- `build.mjs`, `serve.mjs`, `package.json`
- the documents: `README.md`, `SPEC.md`, `BRIEF.md`, `DEPLOY.md`,
  `GITHUB-SETUP.md`, `RECOMMENDATION.md`, `BUILD-CODEMIRROR.md`,
  `AUDIT-REPORT.md`, `GITHUB-PAGES-PROPOSAL.md`

What should **not** be there, and will not be if `.gitignore` is doing its job:

- `node_modules/` (15 MB of development-only packages)
- `dist/` (regenerated by the workflow on every deploy)
- `Claude outputs/` (660 KB of duplicated screenshots)
- `package-lock.json`

If any of those four appear in the list, stop and run `git reset` — nothing is
committed yet, so nothing is stuck. Then check that `.gitignore` is present in
the project folder before trying again.

The documents are published as part of the repository but **not** as part of the
website. `build.mjs` copies an explicit list of files into `dist/`, and the
workflow publishes only `dist/`. `test/dist.browser.mjs` confirms this by
fetching `SPEC.md`, `BRIEF.md`, `package.json`, `serve.mjs` and the test suite
from the built site and requiring all of them to 404.

## Step 4 — The first commit

```
git commit -m "Python turtle editor: complete, tested, ready to deploy"
```

Expect a pause of a few seconds while it hashes `vendor/`.

---

## Step 5 — Create the repository on GitHub

At <https://github.com/new>:

| Field | What to put |
|---|---|
| **Repository name** | `turtle` |
| **Description** | Python turtle editor for intro programming |
| **Visibility** | **Public** (see above) |
| **Add a README file** | **leave unchecked** |
| **Add .gitignore** | **None** |
| **Choose a license** | your call; `None` is simplest |

Then **Create repository**.

The three "leave it empty" choices matter. If GitHub creates any file, the
repository has a commit your local one does not, and your first push is rejected
with a confusing `fetch first` error. An empty repository accepts your history
cleanly.

**The name becomes the URL.** `turtle` gives you
`https://yourname.github.io/turtle/` — short, typable, and a URL a student can
get right from memory or from the board. If you would rather have the bare
`https://yourname.github.io/` with no path, name the repository
`yourname.github.io` instead, using your exact GitHub username. That works
identically, but it uses up your one GitHub user site.

---

## Step 6 — Push

GitHub shows you these two lines on the empty repository page. Use the ones it
shows you — they have your username already in them:

```
git remote add origin https://github.com/YOURNAME/turtle.git
git push -u origin main
```

The first push opens a browser window to sign in to GitHub. Git Credential
Manager, which comes with Git for Windows, remembers it afterwards; you will not
be asked again on this machine.

If it asks for a username and password in the terminal instead, **your GitHub
account password will not work** — GitHub stopped accepting passwords over git
in 2021. Generate a token at **Settings → Developer settings → Personal access
tokens → Tokens (classic)**, give it the `repo` scope, and paste the token where
it asks for a password.

Uploading 14 MB takes a minute or two on school wifi. `Writing objects: 100%` is
the part that takes the time.

---

## Step 7 — Turn Pages on

In the repository: **Settings → Pages**.

Under **Build and deployment → Source**, choose **GitHub Actions**.

That is the entire setting. Do not pick "Deploy from a branch" — the branch
option would publish the repository root, which means the test suite, the
planning documents, and `serve.mjs` would all be live on the site. The Actions
option publishes only what `build.mjs` produces.

There is no Save button on that dropdown; the choice takes effect immediately.

---

## Step 8 — Watch the first deploy

Open the **Actions** tab. The push from Step 6 already started a run called
**Deploy to GitHub Pages**. Click into it.

It takes two to three minutes, and it runs in this order:

1. **Checks that need no browser** — the CSP, sanitiser and share-link suites.
2. **Install a browser** — downloads Chromium for the next two steps.
3. **Student code must not be able to reach the network** — this one starts a
   listening server and has Python running in the editor try to reach it through
   `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `importScripts`, a
   nested worker, and `urllib`. It passes only if *nothing arrives*.
4. **Build `dist/`**.
5. **The built site must work the way Pages will serve it** — serves the built
   folder from a subpath with no CSP header, which is exactly what GitHub Pages
   does, and checks Python still boots, the turtle still draws, the sandbox still
   holds, the service worker still scopes correctly, offline still works, and
   none of the private files are reachable.
6. **Deploy.**

Steps 3 and 5 are the ones that matter. They are the reason a deploy can fail,
and a failed deploy leaves the previous version of the site up rather than
replacing it with a broken one. If either ever goes red, the site does not
change and you have time to look at it.

When the run finishes, the green **deploy** box shows the live URL.

---

## Step 9 — Check the live site yourself

Open the URL. Five things, none of which take longer than a few seconds:

1. **Python starts.** The status line settles and the editor becomes usable —
   five to ten seconds on a first visit, while 6 MB of runtime downloads.
2. **A turtle draws.** Run the starter program.
3. **`speed()` works.** Change `t.speed(0)` to `t.speed(1)` and run again; the
   drawing should be slow enough to watch. This is the one that was broken
   before, so it is worth confirming on the real host.
4. **Errors point at the right place.** Delete a colon and run. You should get
   CPython's own message with a caret under the exact character, and the line
   number should match the editor.
5. **It works offline.** Load the site once, then turn off wifi and reload. The
   editor should start and run Python with no network at all. That is the
   service worker, and it is what makes the tool survive a bad day on the school
   network.

Then reload once more and check the second load is fast — under a second.
Students pay the 6 MB download only on their first visit per browser.

## After that: how you change things

```
git add -A
git commit -m "what changed"
git push
```

The push triggers the workflow; the workflow runs the tests; if they pass, the
site updates in about three minutes. If they fail, the site stays as it was.

Run `npm test` locally before pushing when you have changed anything in `src/`.
That runs the full suite including the animation-timing tests, which are
deliberately left out of CI — they are sensitive to a loaded shared runner and a
flaky failure blocking a deploy would be worse than useless.

**One thing to remember:** if you ever replace anything in `vendor/`, bump
`CACHE_VERSION` in `sw.js` in the same commit. The service worker caches
`vendor/` indefinitely by design, so without the bump, returning students keep
running the old Python.

## When something goes wrong

| What you see | What it is |
|---|---|
| `Updates were rejected... fetch first` on the first push | The GitHub repository was created with a README or licence. Easiest fix: delete it and create a truly empty one, or `git pull --rebase origin main` then push again. |
| `Author identity unknown` | Step 1 was skipped. |
| Push hangs at `Writing objects` | It is the 14 MB of `vendor/`. Give it a few minutes. |
| Actions tab is empty after pushing | Nothing was pushed to `main`. `git branch --show-current` — if it says `master`, run `git branch -M main` and push again. |
| Run fails at **Student code must not be able to reach the network** | A genuine regression in the sandbox. The site is not updated. Do not bypass this one — it is the claim `BRIEF.md` makes to Technology Services. |
| Run fails at the **built site** step | Usually a file added to the project but not to the include list in `build.mjs`. The failure names what 404ed. |
| Run is green, URL 404s | Pages was not switched to **GitHub Actions** in Step 7, or the very first deploy is still propagating — give it five minutes. |
| Site loads but Python never starts | Open DevTools → Network and look for a red `pyodide.asm.wasm`. Almost always means `vendor/` did not get committed; `git ls-files vendor` should list 6 files. |
| Students get an old version after an update | `CACHE_VERSION` in `sw.js` was not bumped. |

## What to send Technology Services

Once the site is live, forward `BRIEF.md` with two additions:

- **the URL**, and the one ask: allowlist `yourname.github.io` on the content
  filter.
- **the repository link.** The brief makes checkable claims — that no AI service
  is contacted, that student code cannot leave the machine, that no server
  receives anything. A public repository means those claims can be read and the
  tests can be re-run by anyone who wants to verify them rather than trust them.

Worth saying plainly in the note: hosting on GitHub Pages means GitHub keeps the
standard web-server logs any host keeps — client IP, timestamp, requested path,
user-agent. No student code, program names, or output ever reaches them, because
the program never leaves the browser. `BRIEF.md` has a section that says exactly
this, written to be forwarded as-is.
