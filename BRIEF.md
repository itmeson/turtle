# Turtle Editor — Review Brief

**For:** Technology / department review
**Prepared by:** Mark Betnel
**Date:** September 2026
**Status:** Built and tested. 331 automated checks, including a suite that actively attempts to exfiltrate student code and passes only if nothing escapes.

---

## What it is

A single-page web tool where students write Python turtle-graphics programs, run them, and see the drawing. It replaces third-party sites (Trinket, replit, online-python.com and similar) currently used in intro programming sections.

It is a **static web page**. There is no application server, no database, and no user accounts.

## Why build rather than buy

The commercial classroom Python sites have converged on a feature set that works against the course:

| Problem | Effect in class |
|---|---|
| AI code assistance enabled by default | Students receive completed answers before attempting the problem. Several sites offer no durable way to disable it. |
| `import turtle` unsupported or partial | The core module of the unit fails or behaves differently than documented. |
| Invisible indentation corruption | Pasted code carries tabs or non-breaking spaces that are visually identical to normal indentation. Students see correct-looking code that will not run, and cannot self-diagnose. |
| Work lost during save/export | Progress disappears mid-period with no recovery path. |

Each of these is a consequence of someone else's product decisions. A locally controlled tool removes the dependency permanently.

## How student code is handled

**All code executes inside the student's own browser.** Python itself is compiled to WebAssembly and runs on the student's machine. There is no server that receives, stores, or processes student work.

This is enforced in two independent layers, both of which can be checked rather than taken on trust.

**First, the Python runtime has no way to reach the network.** After the interpreter finishes loading, the editor removes the browser features that could send data — `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `importScripts`, background workers — from the environment student code runs in. It also removes access to browser storage, so a program opened from someone else's shared link cannot read other saved work on that computer. A program that attempts any of these gets an error; nothing leaves the machine. This is the layer that matters most, because it holds regardless of where the site is hosted.

**Second, a Content Security Policy restricts the page itself** to its own origin (`connect-src 'self'`), so no part of the application can contact a third party — no analytics, no AI service, no telemetry.

Both layers are verified automatically before every deployment. `test/security.browser.mjs` runs a listening server and has student Python attempt to reach it through every available channel; the test passes only if **nothing arrives**. `test/csp.test.mjs` checks the policy itself. These are not assurances in a document — they are checks that fail the build.

Consequences for review:

- **No student PII is collected, transmitted, or stored** by the application. Not names, not email, not activity.
- **No accounts, no logins, no SSO integration required.**
- **No AI model is involved.** There is no inference endpoint, no code completion, and no suggestion feature of any kind. The runtime is physically incapable of calling one.
- **No application backend exists** — no database, no API, nothing that could receive a submission.

Students' work is saved in their own browser's local storage. Sharing a program produces a link that carries the code compressed inside the URL *fragment* — the portion after `#`, which browsers never transmit to a server by design. A shared program therefore never reaches the host at all.

### What the host does see

The site is served as static files, so the hosting provider handles ordinary web requests and keeps the standard logs any web server keeps: **client IP address, timestamp, requested file path, and browser user-agent.** This is the same information generated by visiting any website, and it contains no student code, program names, or output.

This should be stated plainly rather than glossed over: choosing any host — Cloudflare Pages, GitHub Pages, or school-run infrastructure — creates a relationship with that provider for connection logging. It does not involve them in processing student work, because student work never travels to them. If your governance process requires review of the host's standard terms, that review is about ordinary web hosting, not about an application handling student data.

If the site is hosted on school-controlled infrastructure instead, even those logs stay in-house. The application works identically either way.

## What Technology Services would need to do

1. **Allowlist one domain** on the content filter (proposed: a `*.pages.dev` subdomain, or a school-controlled domain).
2. Nothing else. No server provisioning, no accounts, no integration, no software installation on student machines.

The site is 33 static files totalling 15 MB.

**Network profile:** approximately **6 MB** downloaded on a student's first visit — the Python runtime, measured, compressed in transit (12.9 MB on disk). It is then served from browser cache and a service worker on every subsequent visit. A section of 25 students loading simultaneously for the first time is a roughly 150 MB burst, once. Steady-state usage after the first day is near zero.

**Browser requirements:** current Chrome, Edge, Firefox, or Safari on macOS or Windows. No extensions, no plugins, no WebAssembly flags.

## Cost

| Item | Annual |
|---|---|
| Static hosting (Cloudflare Pages free tier — unlimited static requests and bandwidth) | $0 |
| Domain name (optional; a free `*.pages.dev` subdomain works) | $0–15 |
| Compute | $0 — execution happens on student devices |
| **Total** | **$0–15/year** |

The cost does not scale with enrollment. Five sections and five hundred sections cost the same, because the school is serving static files and nothing else.

## Risks and honest limitations

- **Maintenance is ours.** No vendor patches this. Realistically it needs occasional attention when browsers change, perhaps a few hours a year. The upside is that it also cannot change without our involvement.
- **Work is stored per-browser, per-computer.** A student who moves between lab machines does not carry their programs with them; they download a `.py` file or use a share link. On shared lab computers, work stays in the browser profile until cleared.
- **Version 1 is drawing-only.** No `input()`, no keyboard or mouse interaction, no turtle games. Those are possible later but out of initial scope.
- **First load is slow on poor connections** — a few seconds while the Python runtime downloads. After that a service worker keeps it on the device, and the editor starts and runs **with no network at all**.
- **Not a full IDE.** Single file, no package installation, no debugger. This is intentional for an intro course.

## Recommendation

Proceed. The technical risk is low, the cost is effectively zero, the privacy posture is stronger than any hosted alternative, and it eliminates a recurring source of instructional disruption.
